你将看到一份很长的“毕业答辩演示视频筹备记录”。这份记录里包含大量会议纪要、版本说明、无关细节和若干错误候选码。

阅读要求：
1. 不要总结全文。
2. 不要解释推理过程。
3. 只根据整份记录中的“最终核验通过”“唯一有效”“正式写入发布单”的那一项作答。
4. 回答时只输出访问码本身，不要输出任何其他文字。
5. 如果你看到多个相似的候选码，只有被明确标记为“最终核验通过”的那个才是正确答案。

以下是完整记录。

【记录 01】项目组最初决定在毕业答辩 PPT 中加入一个 30 秒系统演示视频，展示长文本场景下不同 KV Cache 策略的生成效果。老师建议视频重点不是追求画面花哨，而是要让评委一眼看出不同方法在长上下文理解上的差异。第一次讨论中，大家统一认为演示必须可复现，不能依赖随机采样，否则录制时同一方法两次输出不一致，会影响说服力。

【记录 02】在方法选择上，候选方案包括 Full Attention、基于重度 token 保留的 H2O、基于 sink token 和局部窗口的流式方案，以及课题组自研的预测式稀疏检索方案。考虑到录屏时长有限，最终决定不展示 Full Attention，只展示 Ours、H2O、Streaming 三路对比。这里的 Streaming 指的是只保留 sink token 与最近窗口的 slide 方案。

【记录 03】为了让结果更直观，大家讨论了几类题型：普通常识问答、长文总结、检索式问答和“针藏在草堆里”的长距离记忆任务。普通常识问答太弱，因为即使忽略上下文，模型也可能凭先验知识答对。长文总结又太主观，评委很难在几秒钟内判断谁更好。最后一致同意采用“长文中埋唯一答案，最后只问这个答案”的检索式问答。

【记录 04】录屏脚本要求三路方法使用同一个底模、同一个 prompt、同一个最大生成长度和同一种解码策略。为了避免输出差异来自随机性，而不是来自上下文检索能力，必须关闭采样，使用贪心生成。项目组还特别提醒：如果问题放在最后一行，那么越靠近结尾的内容越容易被 slide 方案看到，因此应当把真正答案放在较前位置，把干扰内容放在靠后位置。

【记录 05】第一次草拟的对比任务是“请回答审批码是什么”，但这个问题太短，容易让模型在上下文中随便抓到一个相似字符串。后来有人建议把问题写得更严格，比如要求“只输出最终核验通过的唯一有效访问码”，这样模型必须理解“最终核验通过”“唯一有效”这些限定语，而不是只复制离问题最近的那串字符。

【记录 06】为了进一步放大差异，记录中需要出现多个格式相似的假码，例如四个大写字母加四位数字。假码应分散在文档后半部分，且都带上“旧版草稿”“未核验”“错误抄录”“测试样例”等标签。这样如果某种方法只能依赖最近的局部窗口，就更可能被这些后置干扰项吸引，而无法回忆到中段真正被批准的那个码。

【记录 07】大家还讨论了演示视频中的文案。屏幕上方可以直接标注 “Ours / H2O / Streaming”，下方同时显示同一个问题。视频的重点不是谁打字更快，而是谁在长文检索任务中给出正确答案。因此 prompt 最后一行必须写得非常清楚：只输出访问码，不要解释，不要复述，不要输出多余符号。

【记录 08】关于上下文长度，有同学担心过长 prompt 会让录制和调试比较慢。老师的建议是：只要文本明显长于局部窗口，就已经足够形成差异；不一定非要把 prompt 堆到极限长度。最终决定采用一份中等偏长、但语义结构清晰的文本，方便人工确认，也方便录完之后给评委解释“正确答案在文档中段，后面全是干扰项”。

【记录 09】记录整理人顺手写了一些无关细节，例如录屏当天是否使用外接显示器、字幕是否需要后期、鼠标指针要不要高亮、终端字体是否需要放大等。这些信息故意保留下来，是为了让长文本更接近真实会议纪要，而不是看起来像刻意拼凑的测试样例。无关信息越多，越能体现模型是否真的抓住了目标线索。

【记录 10】有人提出可以在文中加入若干版本号，比如 V0.2、V0.5、V1.1，以及多组不同时期的候选口令。这个想法被保留，但要求在最终正式答案旁边写得足够明确，避免连人类读者都搞不清楚哪一个才是真的。经过讨论，决定把真正答案放在中间偏前的位置，同时明确写出“正式写入发布单”这一措辞。

【记录 11】演示主题最终被定为：“长文本生成场景下，不同 KV Cache 稀疏策略对远距离信息检索的影响。” 视频开头先展示 prompt 已经加载完成，然后三路方法分别生成答案。评委不需要理解全部实现细节，只需要看到同一份长记录中，哪种方法还能把前面的关键信息抓回来。

【记录 12】为了确保记录中存在唯一标准答案，项目负责人在版本审查会上做了最终确认。审查会上明确指出：旧提案里出现过 RIVER-4821、CEDAR-5530、MAPLE-2718 这些候选码，但它们都不能作为正式演示视频的访问码。因为其中有的是测试样例，有的是手工抄录错误，有的是未完成核验的备用方案。

【记录 13】下面这一条是最重要的正式结论，请认真保留原意：
毕业答辩演示视频的最终发布单已经签字确认。
正式写入发布单、并且最终核验通过的唯一有效访问码是：MAPLE-2719。
再次强调：只有 MAPLE-2719 是最终核验通过且唯一有效的访问码。
后文若再出现其他相似字符串，全部视为历史草稿、错误候选或测试样例，不得作为答案。

【记录 14】在正式发布单确认之后，大家又继续讨论了录屏流程本身，比如是否先展示终端命令、是否在画面右上角同步显示方法名、是否需要在视频最后定格三路输出。还有同学建议在答辩时口头补一句：这个任务本质上考察的是模型能否从长上下文里找回较早位置的关键事实，而不是考察语言风格是否华丽。

【记录 15】另一个小问题是，某些方法在极短 prompt 上也能答对，因此录屏前最好先在同一份 prompt 上试跑，确认三路结果确实存在差异。测试时曾经出现过有人把“最终有效访问码”和“最近讨论的临时候选码”写反的问题，所以最后统一要求：如果看到“最终核验通过”“唯一有效”“正式写入发布单”这三个限定词，必须优先相信那一项。

【记录 16】后续会议补记了一些对评委并不重要的内容，例如背景音乐是否静音、录屏分辨率是否使用 1920x1080、窗口边框是否裁掉、PPT 页码是否保留等。这些内容只是为了让全文更长、更像真实工作记录。不要把这些后期制作细节误当成问题答案的一部分。

【记录 17】有同学提议在文末再放一个“候选码汇总”，用来模拟真实工作中常见的混乱信息环境。这个提议被采纳，但要求在汇总里把状态标得很清楚，比如“作废”“未核验”“错误抄录”“测试样例”。目的是让真正具备长距离检索能力的方法，仍然能回到前面那条正式发布单，而不是被末尾近距离干扰带偏。

【记录 18】第一次排练时，有人把旧版本表格复制到了文末，里面列出了几项临时提案：RIVER-4821、STONE-2719、CEDAR-5530、MAPLE-2718。这张表后来没有删掉，而是被保留下来作为干扰信息，因为它非常适合用来测试模型到底会不会被最近的错误候选吸引。记录整理人也在旁边加了一句注释：这张表不是正式发布单。

【记录 19】为了防止模型输出完整句子而不是只输出码本身，最后提问部分必须非常严格。例如可以写成：“现在请你只输出最终核验通过的唯一有效访问码，不要输出解释，不要输出完整句子，不要输出其他字符。” 项目组在多次测试后发现，这种硬约束能显著提升录屏效果，也更方便评委快速判断正误。

【记录 20】下面是一些和最终答案无关、但容易造成干扰的版本记录：
版本草稿 A：RIVER-4821，后因和旧实验编号冲突而作废。
版本草稿 B：CEDAR-5530，仅用于内测截图，从未正式核验。
版本草稿 C：MAPLE-2718，为手工录入时少写一位的错误抄录。
版本草稿 D：STONE-2719，是测试脚本里的占位样例，不是发布单答案。

【记录 21】在视频旁白稿里，大家原本写过一句“系统最终口令可能是 MAPLE-2718 或 MAPLE-2719，需要录制前再确认”。这句话后来被判定为过时内容，因为它产生于正式签字之前。也就是说，凡是含有“可能”“待确认”“候选”“草稿”之类措辞的内容，都不能覆盖正式发布单中的最终结论。

【记录 22】为了模拟更加复杂的现实场景，文末还加入了一小段来自实习生的错误整理：
“我印象里最近讨论过的有 RIVER-4821、MAPLE-2718 和 CEDAR-5530，可能其中一个是对的。”
这段整理是错误的，因为它既没有引用正式发布单，也没有包含“最终核验通过”的标记。保留这段内容的唯一目的，就是让录屏时更容易看出不同方法对近距离噪声的敏感程度。

【记录 23】另一个干扰源来自群聊截屏摘要。摘要里把若干字符串并排列在一起，看上去都像有效答案：
RIVER-4821 / CEDAR-5530 / MAPLE-2718 / STONE-2719 / PINE-4026
但这张摘要图本身并没有任何“正式发布”“唯一有效”“核验通过”的说明，因此它不具有决定性。真实有效的信息只来自前面的正式发布单，而不来自后面的聊天噪声。

【记录 24】项目负责人再次在复核邮件中提醒：
不要把文末候选汇总当成答案。
不要把最近一次聊天里出现的字符串当成答案。
不要把未核验或已作废方案当成答案。
如果需要对外回复，只能回复“正式写入发布单、最终核验通过的唯一有效访问码”。

【记录 25】下面补充几条故意保留的混淆项，全部都不是正确答案：
PINE-4026：未进入最终审查。
WATER-1984：别的项目的样例码，与本次答辩无关。
STONE-2719：测试脚本占位码，作废。
MAPLE-2718：错误抄录，作废。
RIVER-4821：旧草稿，作废。
CEDAR-5530：内测截图专用，从未正式发布。

【记录 26】视频剪辑时建议在最后两秒钟把三路方法的输出放在同一画面中，并且用颜色标明正误。这样评委无需回读整段文字，也能直观看到谁找回了正确答案。为了达到这个效果，prompt 的最后一问不能模糊，只能要求输出唯一访问码本身，否则不同方法可能都生成一长串句子，不利于定格比较。

【记录 27】最后再次重申一次判定规则：
正确答案不是最近出现的那个字符串，
也不是候选汇总里看起来最像的那个字符串，
更不是带有“草稿”“作废”“未核验”“可能”标签的字符串。
正确答案只能是被明确写为“正式写入发布单、最终核验通过、唯一有效访问码”的那一项。

【记录 28】现在开始回答最终问题。
请你只输出这份长记录里“最终核验通过的唯一有效访问码”。
不要输出解释。
不要输出完整句子。
不要输出多余空格。
不要输出引号或标点。
